# 玩家战斗状态系统设计

日期：2026-09-12。状态：首版已实现并接入玩家生命、体力恢复。

## 1. 已确定的规则与范围

**战斗状态依据战斗意图及其执行行为判断，不以实际造成或受到伤害为必要条件。** 攻击挥空、释放战斗技能但未造成伤害、伤害被取消、无敌完全阻止扣血，均应进入或保持战斗状态。

“意图”落实为服务器确认开始的战斗动作，或服务器确认成立的敌对交互。原始按键、仅选中目标、无效网络请求不等于已发生战斗行为。

每位玩家只有 NonCombat（非战斗）和 Combat（战斗）两个对外状态。附近存在敌人本身不入战；不进行敌人距离轮询、NetworkObject 全量扫描或空间索引维护。

脱战等待当前默认 5 秒，可在玩家预制体配置。

本系统只管理战斗上下文，体力、回血、音乐、HUD 等通过接口消费状态。倍率、恢复速度和消费等待不进入状态机。

## 2. 已完成的接入

- CorePlayerState 管理 InitialSpawn / Eliminated / Respawned，并采用 Owner 写入。保留生命周期职责，独立建立服务器权威的战斗状态。
- ServerCombatResolutionHost 和原伤害结果路由继续服务要求 AppliedDamage > 0 的消费者；战斗状态使用独立的 ServerCombatActivity 入口。
- CombatAbilityNetworkBridge 在服务器验证身份、序列和基础动作条件后发布动作活动。挥空、零伤害和效果被抑制的已接受动作均能入战；动作校验失败不会入战。
- PlayerCombatReceiver、EnemyNetworkActor、Boss 本体/手部和 CombatStatusHost 在合法敌对交互成立后、免疫和最终伤害结果之前发布交互活动。
- 普通敌人在 Telegraphing 时令明确目标入战；Boss 对明确目标的施法使用持续活动句柄，结束、取消或 Despawn 时释放。
- 激光使用持续活动句柄；使魔开火/冲撞动作归属玩家主人。
- 战斗型可使用物品拥有 CombatIntentPolicy，现有补给默认 NonCombat。
- 遵守 PROJECT_PLAN 的跨模块边界：Contracts 定义端口，Player 实现规则，Infrastructure 适配具体技能、Enemy、Boss 和 NGO。

## 3. 状态和内部数据

```csharp
public enum PlayerCombatState : byte
{
    NonCombat = 0,
    Combat = 1
}

public interface IPlayerCombatStateReader
{
    PlayerCombatState State { get; }
    bool IsInitialized { get; }
    event Action<PlayerCombatState, PlayerCombatState> StateChanged;
}
```

接口为设计示意。消费者订阅后读取当前快照，不只等待变化事件。初始化标记用于避免误用默认 NonCombat。

内部数据：

- 当前状态、存活/初始化标记。
- 最近一次已确认战斗活动时间和脱战截止时间。
- 持续战斗动作的活动句柄集合（例如引导技能）。
- 生命周期版本。
- 有界的事件去重记录；不允许历史事件集合无限增长。

“等待脱战”仍然是 Combat。死亡、复活与战斗状态是独立维度。

## 4. 转换和脱战规则

| 输入 | 行为 |
| --- | --- |
| 生成/复活并完成初始化 | NonCombat |
| 确认开始攻击、战斗技能或其他战斗动作 | 立即 Combat，刷新活动时间 |
| 确认受到敌对攻击/效果交互 | 立即 Combat，刷新活动时间 |
| Combat 中再次收到有效战斗活动 | 保持 Combat，刷新活动时间，不重复通知状态 |
| 持续战斗动作仍在执行 | 保持 Combat，不允许中途脱战 |
| 最后一个持续战斗动作结束/中断 | 从结束时点刷新活动时间，开始脱战等待 |
| 没有持续动作且截止时间到达 | NonCombat |
| 死亡 | 先使生命周期失效，再清理状态、句柄和调度 |
| Despawn / 断线 / 对局结束 | 注销订阅与调度，释放上下文 |

```text
脱战截止时间 = 最近一次战斗活动时间 + 脱战等待秒数
允许脱战 = 没有持续战斗动作 && 当前模拟时间 >= 脱战截止时间
```

例子：t=0 挥空入战；t=3 遭遇敌对命中但无敌未掉血，截止延后至 t=8。之后无战斗活动则 t=8 脱战，即使敌人仍在旁边。t=7 已发射的投射物命中敌人时，再将截止延后至 t=12。

如果 t=0 开始引导且 t=10 才结束，引导期间保持 Combat，结束后默认 t=15 脱战。不靠每帧伪造命中事件维持引导状态。

死亡后 NonCombat 不表示可以恢复。恢复消费者必须额外检查生成、初始化和服务端存活状态；先失效生命周期，再发状态清理通知。

## 5. 各类战斗行为的规则

### 5.1 攻击、技能和敌对交互

| 情况 | 推荐行为与归属 |
| --- | --- |
| 普攻已开始但挥空、远程发射但未命中 | 攻击者入战 |
| 战斗技能已开始，但无目标、无伤害或效果量为零 | 施法者入战 |
| 动作已开始，随后被打断/取消，或伤害被修饰器取消 | 已经入战；持续动作中断时释放句柄并开始等待 |
| 伤害因无敌、格挡、护盾、减免而为零 | 敌对交互已成立则双方所属玩家入战 |
| 敌方已对玩家开始明确指向的攻击，最终挥空/被闪避 | 被针对玩家也入战；须有服务器确认的有效目标和执行上下文 |
| 无明确目标的攻击或范围技能 | 施放者先入战；实际确认触及的敌对玩家各自入战 |
| 仅锁定/选中玩家、AI 索敌、仇恨、靠近或远处动画 | 不足以触发该玩家入战 |
| PvP、Boss 本体/手部攻击 | 使用同一规则，验证敌对关系和有效参与者 |
| 死亡对象、过期实例、非法实体、伪造/重复请求 | 不生成战斗活动 |

“指向玩家”不是客户端随意填入一个 TargetId：必须来自已接受攻击的目标上下文，按技能本身的锁定、范围等规则确认。不存在明确受击对象的挥空，不推测哪个附近玩家“可能被攻击”，也不增加全局感知扫描。

伤害取消分两层处理：

1. 动作已经被确认，伤害或效果结算被取消：算战斗，包括目标无敌、护盾吸收。
2. 动作尚未成立，因冷却、资源不足、死亡、无效技能/权限或请求格式被拒绝：不算战斗。

校验失败不能伪装成“效果取消”，反之也不能把免疫当成“非法目标”过滤，导致合法受击意图漏报。

### 5.2 持续、被动和召唤物

| 情况 | 推荐行为与归属 |
| --- | --- |
| 连击/连续射击 | 每次独立动作开始刷新；命中时也可形成新的交互活动 |
| 引导/持续施法 | 使用 Begin/End 句柄；中断、替换、死亡必须释放 |
| DoT 周期结算 | 每次有效敌对作用尝试刷新双方，免疫/护盾阻止损血仍算 |
| DoT 被解除、到期或本次根本没有作用尝试 | 不因计时器存在而持续锁定战斗 |
| 使魔/召唤物攻击挥空或技能开始 | 归属存活主人，主人入战 |
| 召唤物只跟随、待机 | 不刷新 |
| 被动反击、反伤、控制/减益 | 实际开始执行或敌对作用尝试成立时入战，无需正数伤害 |
| 常驻伤害光环 | 启用为显式战斗动作时刷新一次；之后只在实际敌对作用尝试时刷新 |
| 投射物仍在飞行、陷阱等待触发 | 存在本身不长期锁定 Combat；有效交互发生时再刷新 |

持续动作句柄只用于玩家/召唤物正在执行的有限动作，不用于永久被动、待机召唤物或所有存活投射物，避免永远不能脱战。

### 5.3 治疗、防御、位移和非战斗行为

技能配置需要显式的 CombatIntentPolicy，不能从 damage > 0 推断技能是否属于战斗。攻击/技能默认按战斗动作处理，明确的生活/交互技能才标记为非战斗。普通移动和自动恢复不是技能施放事件。

| 情况 | 推荐行为 |
| --- | --- |
| 主动防御技能、格挡/招架动作、战斗型强化/治疗/复活技能 | 确认开始即令施放者入战，即使效果为零或失败于后续结算 |
| 非战斗辅助技能作用于战斗中的队友 | 成立时令支援者入战；受援者不因被治疗自动延后脱战 |
| 纯生活技能、非战斗辅助作用于非战斗对象 | 不入战 |
| 被动持续治疗、自然恢复、普通容量变化 | 不刷新双方，避免恢复自身维持 Combat |
| 普通疾跑、当前普通移动 Dash | 不入战；带攻击/防御用途的 Dash 由技能配置显式标记 |
| 仅因无敌帧躲过敌对交互 | 交互成立时入战，不依赖 Dash 本身是否标记 |
| 普通拾取、背包操作、普通补给消耗 | 不入战；明确执行战斗效果的物品使用战斗策略 |
| 普通环境伤害、自伤数值调整 | 不自动代表交战；战斗技能代价由动作事件入战，敌对来源陷阱按敌对交互处理 |

以上辅助/位移分类是建议默认值，实施时逐一映射现有技能和物品。不能根据技能名字或输入按键隐式猜测，也不能把“所有回血”都当辅助施法。

自伤和环境扣血仍可重置独立的生命恢复等待；战斗状态与血量变化判定分开。

## 6. 独立战斗活动契约与发布时点

建议新增 CombatActivityEvent 及服务端接收端口，与 CombatResolutionRecord 分工：前者描述动作/交互，后者描述伤害结果。不要为了漏报问题移除原伤害路由的 AppliedDamage 门槛。

事件需要表达：

- ActionCommitted：战斗动作确认开始。
- HostileInteractionConfirmed：敌对接触、明确指向攻击或敌对效果尝试成立。
- SustainedActionBegan / SustainedActionEnded：持续动作的生命周期。
- SupportCommitted：按配置分类的主动支援行为。

建议携带活动种类、源实体/目标实体（可空）、施放者归属、ActionInstanceId、交互子序号/DoT Tick 序号、生命周期版本、服务端确认时间。作用于哪些玩家由服务器适配器依据规则决定，客户端不能直接传入“令某玩家进入战斗”的结果。

一次动作开始和稍后的命中是不同活动，后者允许刷新截止时间；同一条重传 RPC、同一碰撞的重复回调不是新活动。去重键包含活动阶段、动作实例、目标及子序号，不能只用 AttackId 或一次攻击 Sequence，否则会吞掉多目标或 DoT 活动。去重存储有界并随实例结束/生命周期清理。

### 6.1 动作入口改造

在技能执行路径建立清晰的“拒绝 / 接受并开始 / 接受但效果被抑制”等结果，避免用 bool 和正数伤害代替执行状态。

- 在身份、动作可用性等必需条件通过并确认动作开始时发布 ActionCommitted。
- 零伤害技能和已接受但效果取消的动作也必须能够到达该通知点。
- 不能从 CombatAbilityHost.Owner 的 TryActivate 返回值，或仅成功发送 RPC，直接设置权威 Combat。
- 当前兼容期仍依赖客户端计划，实施需明确服务器接受动作的最小校验和序列去重；不能声称现有校验器已经验证了全部冷却/资源。
- 必要时拆分“服务器接受动作”和“执行效果”，让后续效果失败不抹去已经成立的意图；未开始动作的校验拒绝则不发通知。
- 从技能权威执行路径发布，不能依赖动画事件、Presenter 或表现 RPC，否则 Dedicated Server/关闭表现时漏报。

### 6.2 敌对交互入口改造

普通敌人、玩家、Boss、控制/减益效果和周期伤害都要覆盖。

接收路径顺序：验证合法来源/目标及交互成立 -> 发布战斗交互 -> 处理取消/无敌/护盾/减免 -> 应用效果与原伤害结果发布。玩家死亡时的清理优先级高于继续保持 Combat。

对于在更上层就因免疫而拒绝接触的路径，也要将“接触成立”和“免疫阻止效果”分开，不能只在最终 ModifyStat 附近补通知。单纯无效命中请求不触发任何玩家入战。

伤害结果事件不再是入战的必要条件，也不作为无条件第二条重复输入。迁移期间为每条战斗路径明确唯一活动发布位置。

## 7. 架构与调度

```text
动作开始/持续动作 ─┐
敌对交互确认 ─────┼─> CombatActivityAdapter ─> PlayerCombatStateController
主动支援分类 ─────┘                                 │
生命周期、模拟时钟 ─────────────────────────────────┤
                                                   ├─> 服务端只读接口 -> 恢复策略
                                                   └─> 服务器网络快照 -> 客户端
```

| 建议类型 | 职责 |
| --- | --- |
| Contracts / PlayerCombatStateContracts | 状态、只读端口 |
| Contracts / CombatActivityContracts | 活动语义、身份/实例关联、服务端接收端口 |
| Player / State / PlayerCombatStateController | 纯 C# 状态转换、截止时间、持续句柄 |
| Infrastructure / Integration / PlayerCombatActivityAdapter | 接入活动、归属参与玩家、过滤/去重 |
| Infrastructure / Netcode / Player / PlayerCombatStateNetworkBridge | 生命周期接线、服务器发布快照 |
| 配置资产 | 脱战等待、技能/物品的 CombatIntentPolicy |
| 对局级调度服务 | 推进 Combat 玩家到期检查 |

不新建面向全部对象的扫描器或权威 ScriptableObject 广播总线。事件直接路由到已知参与玩家的组件/上下文，缓存归属引用，避免每次遍历所有玩家。

对局调度当前以 20 Hz 遍历已注册玩家，成本 O(P)，P 为本局玩家数；它同时推进状态到期与生命/体力恢复，不遍历 NetworkObject。入战立即事件驱动；退出通常最多晚约一个调度周期，卡顿可能额外延迟。没有每玩家 Update、每活动协程或不断累积的延迟任务。

使用 double 服务端模拟时间，单人暂停不推进脱战计时，多人个人菜单不暂停服务器。当前阶段先处理活动与生命周期输入，再检查到期；尚未到达服务器的行为不追溯修改旧状态。

稳定 Combat 期间仅刷新内部时间/句柄，不重复 StateChanged 或写网络枚举。活动处理成本随实际动作/交互数量增长，不宣称事件驱动没有成本。

## 8. 网络、死亡和异常清理

- 状态和 IsInitialized 组成一致快照，NetworkVariable 仅服务器写入。
- 服务端体力直接读权威状态；客户端消费快照；Host 不重复转发两套变化通知。
- 晚加入通过当前快照初始化，内部活动列表/截止时间无需同步。
- 存活依据来自服务端权威属性或生命周期输入，不把 Owner 写入的 CorePlayerState 当独立权威源。
- 致死交互先让有效参与者入战，随后死亡清理目标；不得在死亡清理后又由迟到伤害结果把死者切回 Combat。存活攻击者照常刷新。
- 复活产生新生命周期版本，旧定时任务、持续动作句柄、缓存归属和重复活动不可直接作用于新生命。
- 旧生命施放的投射物后来命中新生命玩家：新目标可因当前有效交互入战；来源归属必须校验施放生命周期，不把主人新生命误当旧施放者。
- 持续动作 Begin/End 均须幂等；中断、替换、取消、死亡、Despawn、断线、所有者变更均释放句柄。
- 句柄由权威动作拥有并保证终止通知；对预期有限时长动作可设基于动作定义的过期保护，避免漏发 End 永久锁战。可无限引导的动作通过权威取消/生命周期管理，不能随意超时解除。
- 对局服务按 NetworkManager/对局实例创建和释放，不遗留跨局静态集合。

## 9. 体力、回血及旧代码迁移

体力已经只读战斗状态：Combat 倍率 1、NonCombat 倍率 2。以当前基础速率 15/秒计，为 15/秒和 30/秒；倍率属于恢复配置，不属于状态机。

```text
允许恢复 = 已生成 && 存活 && 状态已初始化 && 消费等待已结束
实际恢复速率 = 基础恢复速率 × 当前战斗状态对应倍率
```

普通体力消费后 0.4 秒、Dash 后 0.2 秒、疾跑不重置等待，仍由消费/恢复策略处理。战斗用途 Dash 可以同时触发入战和体力消费，两者是独立规则。

StaminaRegenBoost.cs、.meta、预制体挂载、半径/扫描间隔字段及旧倍率写入路径已删除。没有新增敌人注册表/空间索引，当前只有一个体力倍率来源。

生命恢复已接入同一策略：Combat 使用 HealthStat.regenRate / regenDelay 的固定数值配置，NonCombat 使用当前最大生命值的百分比速率。当前 HealthStat.regenRate 保持 0；非战斗默认每秒恢复最大生命值的 1/60。挥空、施法和无敌受击均会进入 Combat，因此会切换到战斗内固定恢复。

PlayerHealthRegen 已删除。CoreStatsHandler 是唯一数值写入与 NetworkList 同步点，恢复速率和等待由 IStatRegenerationPolicy 决定；对局级 PlayerRecoveryScheduler 以 20 Hz 推进，不存在并行恢复路径。

## 10. 验收与实施顺序

### 逻辑验收

- 初始状态、第一次活动入战、后续活动刷新、到期脱战、稳定状态无重复通知。
- 挥空、零伤害技能、取消伤害、无敌、护盾、格挡均入战。
- 动作开始前被冷却/资源/权限拒绝不入战；开始后中断保持战斗并等待。
- 引导超过脱战时长仍处于 Combat；正常结束、中断、漏 End 保护与多个句柄并存。
- 附近有敌人本身不入战；普通移动/被动恢复不刷新。
- 同一动作开始与后续接触分别有效，重复事件无效，多目标/多 Tick 不被错误去重。
- 主动辅助、战斗型 Dash 与普通 Dash 按配置分类。
- 死亡/复活、持续句柄清理、暂停、到期与新活动的顺序。

### 接线与联机验收

覆盖玩家攻击、敌人攻击、Boss 本体/手部、远程、AoE、DoT、使魔、控制/减益、免疫早退路径。明确指向的挥空只影响已验证目标，无目标攻击不猜测受击者。

关闭表现组件以及 Dedicated Server 下也能正确入战。Host 与远端状态一致，晚加入正确初始化；客户端只提交动作请求，不能直接设置战斗状态。复活后的旧投射物/缓存事件需验证归属。

### 性能验收

无 SpawnedObjectsList 遍历和附近敌人轮询。稳态无重复网络写入，活动不分配协程/延迟任务对象，去重集合与持续句柄集合有界且能清理。高频武器、DoT 和多目标技能下测量 CPU、GC 与状态同步次数。
